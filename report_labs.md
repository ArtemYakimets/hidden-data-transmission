# План рассказа по лабораторным работам №1 и №3

Документ предназначен для подготовки к защите: общая схема работы стенда, пошаговый план выступления, комментарии к ключевым функциям и к выводу программ.

---

## 1. Общая схема: как всё устроено

### 1.1. Роли узлов

| Узел | ВМ (IP) | Роль |
|------|---------|------|
| **П1** | `p1`, 192.168.56.10 | Легитимный пользователь + **закладка** (`sender.py`) |
| **УЗ** | `uz`, 192.168.56.11 | **Устройство защиты** (`security_device.py`) |
| **П2** | `p2`, 192.168.56.12 | Легитимный получатель + **злоумышленник** (`receiver.py`) |

Логически закладка и П1 — одна сущность; злоумышленник и П2 — одна сущность (как в методичке).

### 1.2. Два канала связи

```text
                    TCP :9000 (управление)
  П1 ──────────────────► УЗ ──────────────────► П2
       JSON: START / END       прозрачная ретрансляция

                    UDP :9001 (данные)
  П1 ──────────────────► УЗ ──────────────────► П2
       датаграммы            ЛР1: без изменений
                             ЛР3: нормализация / паддинг
```

- **TCP** передаёт параметры сеанса: сколько символов, `L`, `n`, интервал, размер буфера. УЗ в ЛР1 и ЛР3 **не меняет** TCP — только пересылает байты.
- **UDP** несёт полезную нагрузку случайных байт; **скрытая информация кодируется только длиной** датаграммы (пример 5 из методички).

### 1.3. Временная последовательность (один сеанс)

```text
  П1                    УЗ                    П2
   │                     │                     │
   │──── TCP connect ───►│──── TCP connect ───►│
   │──── START (JSON) ─►│────────────────────►│  П2 запоминает num_symbols, L, n, ...
   │                     │                     │
   │  sleep SYNC_DELAY   │                     │  П2: t0 = now + SYNC_DELAY (ожидание UDP)
   │                     │                     │
   │──── UDP: N скрытых пакетов (интервал T) ─►│  Collector пишет (время, длина)
   │──── UDP: фиктивные пакеты ───────────────►│
   │                     │                     │
   │──── END (JSON) ────►│────────────────────►│  П2: стоп сбора, декодирование
   │                     │                     │
```

**Важно для объяснения на защите:** сначала идут все **скрытые** пакеты (фиксированный шаг по времени — модель 3), затем **фиктивные**. Приёмник берёт **первые `num_symbols` пакетов по времени прихода** — это и есть скрытые; остальное — шум.

### 1.4. Идея скрытого канала (пример 5)

- Заданы \(L\) (макс. длина в байтах) и \(n\), причём \(n \mid L\).
- Алфавит: \(\frac{L}{n}\) символов. Символ с номером \(i\) кодируется длиной \(l\), где \((i-1)n < l \le in\).
- В коде символы **0-индексированы**; длина выбирается случайно в допустимом диапазоне — имитация «случайной длины» при фиксированных моментах отправки.

### 1.5. Запуск демонстраций с хоста

1. `run.bat` / `./run.sh` — поднять все ВМ (`vagrant up`).
2. `run_lab1.bat` / `./run_lab1.sh` — ЛР1 (УЗ в режиме `passive`).
3. `run_lab3.bat` / `./run_lab3.sh` — ЛР3 (две схемы подряд, **без** перезапуска ВМ).

На ВМ фоновые процессы стартуют через `start_daemon.py`, чтобы процесс пережил закрытие SSH-сессии.

## 2. План рассказа: Лабораторная работа №1

**Цель:** показать скрытый канал по длинам пакетов, пассивное УЗ, корректное декодирование.

### 2.1. Вступление (1–2 мин)

- Формулировка: два пользователя, между ними УЗ; в П1 закладка; П2 «слушает» и извлекает скрытое сообщение.
- В ЛР1 УЗ — **заглушка**: только пересылает трафик.

### 2.2. Демонстрация (2–3 мин)

- Уже подняты ВМ → запустить `run_lab1.bat` / `run_lab1.sh`.
- Кратко проговорить порядок скрипта: очистка старых процессов → `receiver` на П2 → `security_device --mode passive` на УЗ → `sender` на П1.

### 2.3. Разбор кода (ключевые места)

#### `common.py` — математика канала

| Функция | Назначение | Комментарий для защиты |
|---------|------------|-------------------------|
| `encode_symbol(symbol, n, L)` | Длина UDP-пакета для символа `symbol` (0…) | Переводит в 1-индекс \(i = symbol+1\), выбирает случайное \(l \in ((i-1)n+1, in]\), не выше `L`. |
| `decode_symbol(length, n)` | Символ по длине | Формула \((l-1)//n\) соответствует восстановлению номера диапазона. |
| `message_to_symbols` / `symbols_to_message` | Байты ↔ символы | При алфавите ≥256 — побайтово; иначе перевод в систему счисления с основанием `alphabet_size`. |
| `send_control` / `recv_control` | Протокол по TCP | 4 байта длины (big-endian) + JSON; так П2 узнаёт `num_symbols`, `L`, `n` без привязки к содержимому UDP. |

#### `sender.py` — П1 + закладка

| Блок / функция | Комментарий |
|----------------|-------------|
| `parse_args()` | `-m`/`-f` — секрет; `-L`, `-n`, `-T`, `--buffer-size`, `--dummy-rate` — параметры канала и трафика. |
| Проверка `L % n == 0` | Условие из методички \(n \mid L\) (в байтах). |
| Цикл `tcp.connect` с retry | УЗ может подняться чуть позже приёмника; иначе `Connection refused`. |
| `send_control(..., "start", ...)` | Передаёт на П2 все параметры декодирования. |
| `time.sleep(SYNC_DELAY)` | Общая пауза после START, чтобы П2 успел выставить окно ожидания. |
| Фаза 1: цикл `while idx < total` | **Модель 3:** пакеты в моменты `t0 + burst_num * interval`; длина — `encode_symbol`; тело — `os.urandom(pkt_len)` (видимый трафик «случайный»). |
| Внутри бурста `BURST_DELAY` | **Буферизация:** при `--buffer-size > 1` несколько символов подряд с малым интервалом. |
| Фаза 2: dummy | `num_dummies = max(1, int(total * dummy_rate))` — фиктивный трафик **после** скрытых пакетов. |

#### `security_device.py` — УЗ (ЛР1)

| Функция | Комментарий |
|---------|-------------|
| `tcp_forward` | Принимает от П1, коннектится к П2, копирует поток байт как есть. |
| `udp_forward` (режим `passive`) | `recvfrom` → `sendto` без изменения `data`; длина на П2 совпадает с длиной на П1. |

#### `receiver.py` — П2 / атакующий

| Класс / функция | Комментарий |
|-----------------|-------------|
| `PacketCollector` | Фоновый поток: для каждой датаграммы сохраняет `(timestamp, len(data))`. |
| `decode_covert` | Сортирует по времени, берёт **первые** `num_symbols` записей, для каждой длины вызывает `decode_symbol`. |
| После `END` | `symbols_to_message` → восстановление исходных байт; счётчик «covert / dummy» по числу пакетов. |

#### `start_daemon.py`

| Функция `main()` | `subprocess.Popen(..., start_new_session=True)` — дочерний процесс не привязан к SSH; лог в файл; краткая проверка, что процесс жив (`poll()`). |

### 2.4. Что показать в выводе (ЛР1)

**П1 (`sender.py`):**

```text
[*] L=1024  n=4  alphabet=256  interval=0.5s  buffer=1
[*] Message: 25 bytes -> 25 symbols
[*] START sent, syncing 2.0s ...
[*] Sent 25/25 symbols
[*] Sending 50 dummy packets ...
[*] Done — 25 covert + 50 dummy packets sent
```

**Как комментировать:** первая строка — параметры канала; вторая — сколько байт и сколько символов (при 256 символах на пакет — 1:1); прогресс — отправка скрытых; затем явно указано количество фиктивных пакетов.

**П2 (`receiver.py`, типичный успех):**

```text
[P2] UDP collector listening on :9001
[P2] TCP control listening on :9000
[P2] Control connection from ('192.168.56.11', ...)
[P2] START — 25 symbols, L=1024, n=4, T=0.5s, buf=1
[P2] END received, decoding ...
[P2] Packets: 75 total, 25 covert, 50 dummy
[P2] Decoded bytes (hex): 48656c6c6f2066726f6d20636f76657274206368616e6e656c
[P2] Decoded message: Hello from covert channel
[P2] Saved to /tmp/decoded.txt
[P2] Done
```

**Как комментировать:** `75 total = 25 + 50` согласуется с отправителем; hex совпадает с UTF-8 строки «Hello from covert channel»; в пассивном режиме текст совпадает с исходным.

**УЗ:** строки о режиме `passive`, портах TCP/UDP, одном сеансе TCP — без SUMMARY (он появляется в ЛР3 при SIGTERM).

### 2.5. Возможные вопросы (короткие ответы)

- **Почему скрытые пакеты не смешиваются с фиктивными при декодировании?** — Потому что фиктивные отправляются **после** всех скрытых; при сортировке по времени первые N — скрытые.
- **Что такое модель 3?** — Случайная длина (в пределах диапазона символа), **фиксированные** моменты отправки (шаг `interval`).
- **Зачем TCP?** — Согласование параметров (`L`, `n`, число символов) без внедрения этих данных в UDP (в учебном стенде — отдельный канал; в реальной атаке параметры могли бы быть заранее оговорены).

## 3. План рассказа: Лабораторная работа №3

**Цель:** УЗ — не заглушка; две схемы превентивного противодействия; оценка влияния на скрытый и на основной канал.

### 3.1. Вступление (1–2 мин)

- Закладка и УЗ — **разные** логические устройства (уже было в топологии; теперь УЗ **активно** меняет UDP).
- Две схемы:
  1. **Ограничение пропускной способности** скрытого канала — нормализация длин до кратного `k`.
  2. **Полное устранение** канала по длине — дополнение всех пакетов до фиксированной длины `L`.

### 3.2. Демонстрация (3–5 мин)

- Запустить `run_lab3.bat` / `run_lab3.sh` (ВМ уже подняты).
- Скрипт делает **два прогона** с одним и тем же текстом:
  1. УЗ: `--mode normalize --k 32`
  2. УЗ: `--mode pad --max-len 1024`
- Показать разницу в логе П2 и блоке **SUMMARY** УЗ после `SIGTERM`.

### 3.3. Разбор кода (ключевые места)

#### `security_device.py` — активные режимы

| Участок | Комментарий |
|---------|-------------|
| `parse_args`: `--mode`, `--k`, `--max-len` | Выбор схемы и численных параметров. |
| `udp_forward`, ветка `normalize` | `target = ceil(orig_len / k) * k`; если длина не кратна `k`, дописывается `os.urandom(target - orig_len)`. **Наблюдаемая** длина на П2 становится кратной `k` → меньше различимых длин → меньше бит на пакет. |
| `udp_forward`, ветка `pad` | Если `orig_len < max_len`, дополнение до `max_len`. Все пакеты одной длины → по длине передать можно только один «символ» → канал по длине исчезает (для декодера все длины равны). |
| `_summary` (обработчик `SIGTERM`) | Считает `overhead = (sum_mod - sum_orig) / sum_orig * 100` — **влияние на основной канал** (объём трафика). `run_lab3` шлёт `SIGTERM` в конце прогона, чтобы вывести статистику. |
| `tcp_forward` | Без изменений: управление не трогаем (в фокусе — манипуляция UDP). |

#### Поведение приёмника без изменения протокола

- `receiver.py` не знает режим УЗ. Он по-прежнему интерпретирует длины как в ЛР1.
- После **normalize** длины «сжимаются» к сетке кратности `k` → те же формулы `decode_symbol` дают **другие** байты → искажённый текст.
- После **pad** длина почти всегда `max_len` → `decode_symbol` даёт один и тот же символ (для L=1024, n=4 — значение 255) на каждый пакет → сообщение нечитаемо.

### 3.4. Что показать в выводе (ЛР3)

**Схема 1 — нормализация (пример):**

П2:

```text
[P2] Decoded message: Ogooo'gwoo'gowgww'gogoogo
```

УЗ (после SIGTERM, фрагмент):

```text
[UZ] === SUMMARY ===
[UZ] Mode: normalize
[UZ] Packets forwarded: 75
[UZ] Bytes original: ...
[UZ] Bytes after modification: ...
[UZ] Overhead: ~2.8%
[UZ] Normalization step k=32
```

**Комментарий:** пропускная способность скрытого канала по длине падает: эффективный алфавит «снаружи» ближе к \(L/k\), а не \(L/n\); сообщение искажено; **overhead основного канала** небольшой.

**Схема 2 — паддинг (пример):**

П2:

```text
[P2] Decoded bytes (hex): ffffffffffffffffffffffffffffffffffffffffffffffffff
[P2] Cannot decode as UTF-8 (25 bytes)
```

УЗ:

```text
[UZ] Mode: pad
[UZ] Overhead: ~128%
[UZ] Fixed length L=1024
```

**Комментарий:** канал по длине **устранён** (все длины одинаковы); цена — резкий рост объёма UDP-трафика (основной канал в нагрузочном смысле страдает сильнее).

### 3.5. Сводная таблица для вывода на слайд / устно

| | ЛР1 (passive) | ЛР3 normalize | ЛР3 pad |
|---|---------------|---------------|---------|
| Скрытый канал | Работает | Искажён / ограничен | Устранён |
| Пропускная способность СК | до log₂(L/n) бит/пакет | ниже (сетка k) | ~0 |
| Overhead основного канала | ~0% | низкий | высокий |

### 3.6. Вывод для защиты (1 мин)

- **Normalize** — разумный компромисс: сложнее передать секрет без ошибок, мало платим по трафику.
- **Pad** — максимальная защита по длине, но дорого по полосе/объёму.
- Применимость: зависит от политики безопасности и допустимых накладных расходов.
